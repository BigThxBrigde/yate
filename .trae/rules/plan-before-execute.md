# plan-before-execute（先方案后执行）

本规则约束本仓库内**非平凡编码任务**的执行方式：方案先行，批准后动代码。
目的：避免"边写边设计"造成的返工、架构偏离与不可追溯的决策。

## 一、判据：什么算"复杂任务"

满足**任一**条件即必须走本流程：

1. 预计改动 ≥ 3 个文件（测试文件不计入判据，但方案里要列出）；
2. 涉及跨层 / 跨模块交互，或触碰架构边界规则（`architecture-boundaries.md`）；
3. 存在多个可行方案、需要选型或架构权衡；
4. 需要先调研代码才能确定做法（无法凭任务描述直接写出 diff）；
5. 用户明确要求先出方案。

不满足以上全部的（单文件小修、用户已给完整逐步指令的任务）可直接执行，但仍须先读目标代码再改。

## 二、硬性流程

1. **调研先行**：先读代码、跑只读探针取证，把关键事实整理成清单（每条带 `文件:行号`）。禁止凭假设设计。
2. **方案落盘**：写入 `.trae/documents/<task>-plan.md`（文件命名与各类文档
   命名及路径引用约定见 `doc-conventions.md`），必须包含：
   - 目标与非目标；
   - 备选方案与**否决理由**（至少列出被放弃的路线）；
   - 分步实施计划，每步含：输入、改动文件清单、输出、**可执行的验收命令**；
   - 风险清单与回滚路径；
   - 涉及业务流程 / 架构 / 模块交互时，配套 Mermaid 图（flowchart / sequence）。
3. **用户批准**：以 NotifyUser 提交方案文档，等待确认。**未经批准不得进入实施**。
4. **按步骤执行**：偏离方案（阈值、范围、选型）必须显式列出并给出实测依据，不得静默改设计。
5. **收尾**：全量门禁（pyright + pytest + 架构守护）→ 计划文档回填真实结果与偏离记录 → 提交。

## 三、禁止事项

- 禁止跳过方案文档直接开写复杂任务；
- 禁止先写代码再补方案（事后补写 = 没写）;
- 禁止方案里出现模糊步骤（"优化 X"、"完善 Y"）而无验收标准；
- 禁止把"用户批准"替换为自我判定"方案显然可行"。

## 四、与其他规则的关系

- **`task-orchestration.md` 优先**：本规则触发时，先检查是否同时满足
  `task-orchestration.md` §一的触发条件（满足本规则 §一任一判据，或用户消息含
  「新任务」「新issue」「新计划」关键字）——若满足，**直接改走
  `task-orchestration.md` 的闭环流程**，本规则的 §二流程不再单独执行，
  其"方案先行"要求由闭环流程第 2 步【方案】承接。
- 与 `subagent-workflow.md` 互补：本规则管"何时动手"，后者管"如何并行"。
- 方案文档是子代理任务书的"唯一规范来源"（见 subagent-workflow §二）。
