## 三、核心问题清单

**本轮未发现「致命 / 严重」级缺陷。** 历史 Critical（`:wq` 保存失败退出、LSP `_read_loop` 挂起、`register_server` 竞态等）已全部修复并带守卫测试（见 [review.md](review.md)）。以下为经实读复核确认成立的**建议级**问题，按影响排序：

### 1. ConPTY 句柄跨线程关闭竞态（理论性，未定义行为类）
- **位置**：[pty_proc.py:600-636](../../yate/editor_term/pty_proc.py#L600-L636) 与 [pty_proc.py:564-568](../../yate/editor_term/pty_proc.py#L564-L568)
- **维度**：健壮性 / 并发
- **问题**：`_ConPty.write`（读 `self._in_write`）与 `resize`（读 `self._hpc`）均不加锁；而读线程经 `_finished → close()`（关闭 `_in_write`/`_out_read`，无锁）与 `_watch_exit → _close_pty()`（有 `_hpc_lock`）在另一线程关闭同一批句柄。`_hpc` 的判空与 `ClosePseudoConsole` 之间、`_in_write` 的判空与 `WriteFile` 之间存在 TOCTOU 窗口。
- **后果**：Windows 句柄值在 `CloseHandle` 后可能被立即复用，极端时序下 `WriteFile`/`ResizePseudoConsole` 会作用到无关内核对象；通常仅表现为被外层 `except OSError` 吞掉的失败，但属未定义行为类隐患（终端退出瞬间仍在敲键才可能触发）。
- **建议**：将 `_hpc_lock` 扩展为覆盖 `_in_write`/`_out_read` 的实现级锁，`write`/`resize`/`close` 统一持锁并在锁内做「快照句柄 → 判空 → 调用」；或把 ctypes 句柄封装为带锁 RAII 小类。

### 2. 补全 worker 的残余异常静默路径
- **位置**：[completion.py:152-157](../../yate/completion.py#L152-L157)（`exit_on_error=False` + `_worker` 无 try/except）、[manager.py:438-444](../../yate/editor_lsp/manager.py#L438-L444)
- **维度**：健壮性 / 可观测性
- **问题**：`request_completion` 已捕获 `LspError / OSError / CancelledError` 返回空列表（复核属实），但 `_unwrap_completion` / `_parse_completion_item` 解析畸形服务器响应时抛出的其它异常会沿 `_worker` 冒泡，被 `exit_on_error=False` 抑制，无任何用户可见反馈。
- **后果**：畸形 LSP 响应下补全静默失效，排查困难。
- **建议**：`_worker` 体内包一层 `except Exception`（`noqa: BLE001` + `log.exception` + `prompt.write` 提示），或在 manager 解析段窄化捕获。

### 3. 语法高亮静默降级零日志
- **位置**：[languages.py:142](../../yate/editor_syntax/ts_backend/languages.py#L142)（`_load_builtin` 失败返回 `None`；全文件无任何 `log` 调用，grep 核实）
- **维度**：健壮性 / 可观测性
- **问题**：tree-sitter 不可用、grammar 模块缺失、query 文件损坏或 import 失败时，一律静默回退 regex 高亮，日志与 UI 均无感知。
- **后果**：用户以为"高亮就是这样"，语法增强形同虚设且无从发现原因。
- **建议**：失败路径 `log.warning`（按语言去重，只报一次），可选经 prompt 提示"语法高亮已降级"。

### 4. 扩展 `setup()` 中途失败留下半注册状态
- **位置**：[extensions.py:386-440](../../yate/services/extensions.py#L386-L440)
- **维度**：健壮性
- **问题**：防护已较好（`sys.modules` 残留清理、teardown 钩子成功后才捕获、`log.exception`——复核属实），但若用户 `setup(api)` 注册了部分 action/command 后抛异常，注册表不回滚，残留半注册能力。
- **后果**：失败扩展的部分命令仍可被调用，行为不一致；触发面窄（仅用户代码 setup 中途抛错）。
- **建议**：最低成本方案是在扩展文档中明示"setup 抛异常前注册的能力不保证回收"；彻底方案为 `ExtensionContext` 提供注册快照/回滚。

### 5. `editor.py` 组装职责过载（1323 行）
- **位置**：[editor.py:83-203](../../yate/editor.py#L83-L203)（构造函数集中组装 session / workspace / LSP / keymaps / 注册表 / 扩展 API / UI / completion）
- **维度**：可维护性 / 可扩展性
- **问题**：与架构规则"`Editor` 只新增横跨多个协作者的操作"存在张力；新功能倾向继续往 `Editor` 里堆。
- **后果**：耦合持续增长，改动半径扩大。
- **建议**：按规则三-6（"能用函数就不造类"）把组装逻辑拆为模块级工厂函数（如 `build_completion_controller(...)`），`Editor` 只保留生命周期与调度；不新建协议层。

### 6. 测试失败路径断言偏弱
- **位置**：[test_app_textual.py:3735-3796](../../tests/test_app_textual.py#L3735-L3796)、[test_app_textual.py:3851-3903](../../tests/test_app_textual.py#L3851-L3903)（`:wq` 失败场景只断言"不退出/文本保留"）；[test_action_table.py:123-167](../../tests/test_action_table.py#L123-L167)（cut/copy 仅成功路径）
- **维度**：测试质量
- **后果**：回归保护集中在 happy path，错误消息/prompt 状态机回归可能漏网。
- **建议**：对关键失败分支补消息级与状态级断言（`save failed` / `unsaved changes`、`doc.modified`、prompt mode）。
